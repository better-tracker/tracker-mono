# Contracts Package

## Overview:
- Contracts package contains shared schemas used by the project tracker app.

- Ensurees the front and backend agree on the structure of the data sent through the API.

- The package uses zod to validate data and generate typescript types from schemas. This helps prevent invalid information from being accepted and reduces the need to define the same data structure multiple times.

- Contracts packagage contains schemas for porjects, subtasks, users and API error responses.

- All schemas are stored in src/ directory and exported through src/index.ts.

## Project Schemas:
- These schemas are defined in src/projects.ts, which validates data used when creating, updating, retrieving, and listing projects.

### Project Creation:
- **Schema**: `projectCreateSchema`
- Used to validate info submitted when creating a new project.
- Project names are trimmed to remove whitespace at beginning and end.
- Project id and creation date are generated by the server and are not included in creeation request.

### Project Update:
- **Schema**: `projectUpdateSchema`
- Used when replacing an existing project's info using a PUT request.
- Both name and description must be provided
- Name must follow same validation rules as project creation, description can be null.

### Project List Response:
- **Schema**: `projectListResponseSchema`
- Defines an array of project summaries.
- Each project has an id, name, description, and creation date.
- The list response does not include nested subtasks array.

## Subtask Schemas:
- Subtask schemas are defined in src/subtasks.ts.
- Validates data when creating, updating, retrieving and listing subtasks.

### Subtask Creation:
- **Schema**: `subtaskCreationSchema`
- Subtask descriptions are trimmed to remove surrounding whiute spaces.
- If completed field is not provided, zod assigns false as a default.
- Server generates the subtask id and timestamps.

### Subtask Update:
- **Schema**: `subtaskUpdateSchema`
- Defines info returned by API for a subtask.

### Subtask List Response:
- **Schema**: `subtaskListResponseSchema`
- Defines an array of subtask responses.
- Each subtask in array must pass same validation rules as an indiviual subtask response.

## User Schemas:
- User schemas defined in src/users.ts
- Validate info used when creating, updating, retrieving, and listing users.

### User Creation:
- **Schema**: `userCreateSchema`
- Username field named user_name to match db structure
- Password validation currently requires nonempty string, additional password complexity such as hashing not involved in this schema.
- Passwords must be hashed by backend before being stored in database.

### User Update:
- **Schema**: `userUpdateSchema`
- Requires user_name and email.
- Profile_pic field is optional and may be set to null.
- Update schema does not include a password field.

### User Response:
- **Schema**: `userResponseSchema`
- Defines info returned when retreiving a user.
- Passwords are excluded from user responses to prevent sensitive info from being returned via API.
- User timestamps not included in current schema, based on supreme leader's decision.

### User List Response:
- **Schema**: `userListResponseSchema`
- Defines an array of user response ojects.

## Validation Rules:
- Zod is used to check whether incoming and outgoing data match expected structure.
- Main validation rules are:
    - Project Name: Required, 1-255 characters after trimming.
    - Project Description: Maximum 2000 characters, nullable.
    - Subtask Description: Required, 1-2000 characters after trimming.
    - Completed: Boolean value.
    - Username: Required, maximum 25 characters.
    - Email: Valid email address.
    - Password: Nonempty string.
    - ids: Valid UUID format.
    - Project and subtask dates: UTC ISO 8601 date strings.

### Required, Optional, and Nullable Fields:
- **Required**: Field must be provided.
- **Optional**: Field may be ommitted.
- **Nullable**: Field may explicitly contain null.

- When validation fails, zod provides info about the invalid fields.

## Error Response Structure:
- API error responses use shared schema defined in src/errorstructure.ts.
- **Schema**: `errorResponseSchema`
- Expected structure is:
    - {
        "error": {
            "code": "VALIDATION_ERROR",
            "message": "Invalid project name"
        }
    }

- Error object contains:
    - code: String identifying the type of error
    - message: String explaining what went wrong.

- Using a consistent error structure allows front and backend to handle errors in the same way.

- The current schema validates error structure but does not restrict error codes to a predefined list.

## IDs and Date Formats:
- **UUIDs**:
    - Projects, subtasks, and users use UUIDs  as unique identifiers.
    - Zod validates UUID strings using z.uuid().
    - IDs are generated by server rather than supplied in creation requests.

- **UTC Dates**:
    - Project and subtask responses use ISO 8601 date strings in UTC.
    - Example:
        - 2026-10-07T00:00:00.000Z
            - Z indicates UTC time.
    - Date strings containing timezone offsets, such as +10:00 are rejected by current schemas.
    - Server is responsible for generating creation and update timestamps.
    - User responses do not currently contain timestamps.

## Running tests:
- Automated tests are located in packages/contracts/tests/.

- Tests use node.js's built in test runner and zod's `safeParse()` method to check whether schemas accept valid data and reject invalid values.

- Test files include:
    - `projects.test.mjs`: Tests project creation, updates, responses, lists, UUIDs, and dates.
    - `subtasks.test.mjs`: Tests subtask creation, updates, responses, lists, and validation rules.
    - `users.test.mjs`: Tests user creation vaidation.
    - `errorstructure.test.mjs`: Tests shared API error response format.

### Run Automated Tests:
- From repo root:
- `pnpm --filter @project-tracker/contracts test`
    - The test command builds the contracts package before executing tests.
    - At this current point in time of writing, package contains 29 automated tests.

### Run ESLint:
- `pnpm --filter @project-tracker/contracts lint`
    - Checks source code for linting issues.

### Run TypeScript Type Checking:
- `pnpm --filter @project-tracker/contracts typecheck`
    - Checks for typescript errors without generating build files.

### Build the Package:
- `pnpm --filter @project-tracker/contracts build`
    - Compiles typescript source code into the dist/ directory.

## Using Contracts Package:
- Contracts package is shared across project tracker monorepo.
- Other packages and apps can import schemas and types using:
```ts
import {
    projectCreateSchema,
    subtaskCreateSchema,
    userCreateSchema
} from '@project-tracker/contracts';
```
- Schemas can validate data using zod's `safeParse()` method.
- If validation succeds, `result.success` is true and validated data is available through `result.data`.
- If validation fails, `result.success` is false and validation errors are available through `results.error`.
- The package also exports typescript types inferred from zod schemas.

- The contracts package only defines and validates data structures. DB operations, API route handlers, and user interface components are handled by their respective packages and apps.
